## 1. Executive summary

HADOTA is a browser-based Arabic/English AI assistant that runs locally on the developer's Windows PC. A single FastAPI application serves both the static frontend and API on the same origin. The backend reuses the existing conversation, prompt/context-management, runtime, and structured-output components. Inference is performed by the existing local Ollama installation using the configured Qwen model.

The current scope is intentionally local-first:

- One local FastAPI application serves the web UI and API.
- Visitors are assigned temporary anonymous sessions; there is no registration, login, username, or shared-password flow.
- Conversations are isolated by session and are stored in process memory, not a database.
- The supported web chat path is **non-streaming request/response**. Browser SSE/fetch streaming is not claimed as implemented.
- The application includes bounded request sizes, message limits, session/conversation caps, session expiry, rate limits, and a single active generation slot.
- The test suite includes unit tests, mocked-runtime tests, web/session tests, and real local-Ollama smoke tests.
- Public internet sharing, Tailscale Funnel, Vercel, and cloud-hosted inference are deferred until separate infrastructure is available and the public-use safety gates can be completed.

## 2. Architecture

```text
Browser (HTML / CSS / JavaScript)
          |
          | same-origin HTTP requests; anonymous HttpOnly session cookie
          v
FastAPI / Uvicorn — 127.0.0.1:8000
  |-- serves frontend files
  |-- validates API payloads and request Origin
  |-- manages anonymous sessions and conversation ownership
  |-- applies request, session, generation and rate limits
  |-- translates failures into safe HTTP responses
  |-- exposes liveness and readiness endpoints
          |
          v
SessionManager + ConversationEntry operation locks
          |
          v
ConversationService
  |-- conversation history / failed-turn handling
  |-- prompt and context preparation
          |
          v
OllamaRuntime
          |
          v
Ollama — http://127.0.0.1:11434 — qwen3.8:27b
```

### Process and data boundaries

- The web server is intended to listen on `127.0.0.1:8000` for local development.
- Ollama is a separate process and normally uses port `11434` for its API.
- The web backend calls the local Ollama runtime; the browser should not call Ollama directly.
- Session and conversation state are process-memory data. Restarting FastAPI clears the in-memory registry and history.
- There is no database, durable user account, cloud inference endpoint, or cross-device conversation history in the current scope.

## 3. Implemented capabilities

### Conversation experience

- Arabic-first chat UI with Arabic, English, and mixed-language text support.
- Separate conversations and a New Chat action.
- A conversation list and conversation retrieval within the current anonymous session.
- Copy-response action.
- Continuation support where the prior generation indicates that the response can continue.
- Busy, failure, and retry states.
- The retry path reuses the existing user-message element rather than rendering a second visible copy.
- If a continuation finishes after navigation, the UI reloads the active transcript so the completed answer is shown in the correct conversation.
- User-confirmed navigation while a response was generating; the final response appeared in the correct conversation.

### Anonymous sessions and history

- No registration or login UI.
- An opaque server-generated session cookie with `HttpOnly` and `SameSite` protections.
- Server-side conversation ownership checks; knowing a conversation ID alone is not sufficient to access it.
- Session and conversation registries held in memory.
- Best-effort page-close cleanup through `POST /api/session/close`, with a grace period so a refresh/new request can preserve the session.
- Explicit session termination through `DELETE /api/session`.
- Idle and absolute TTL expiry remain authoritative cleanup mechanisms; browser close signals are not reliable enough to be the only cleanup method.

### Runtime reliability and resource controls

- Thread-safe conversation-history operations.
- Rollback handling for failed or incomplete generation turns in the inspected normal, streaming-service, and structured-output paths.
- Per-conversation operation locks and non-blocking busy responses.
- One active model generation globally; a competing generation receives a retryable busy response instead of creating unbounded model work.
- Per-session and process-wide sliding-window generation limits.
- Request-body byte limit enforced before payload parsing, including chunked bodies without `Content-Length`.
- Message-character, active-session and per-session conversation limits.
- Separate liveness (`/api/health`) and runtime/model readiness (`/api/ready`) checks.
- Generic validation errors, request correlation IDs, and `X-Content-Type-Options: nosniff` / `Referrer-Policy: no-referrer` response protections.
- Public-mode configuration validation that requires secure cookies, valid HTTPS origins, bounded resource limits, and one active generation.

### Safe response formatting

When the local `marked` and DOMPurify assets are present, Markdown is rendered through the configured safe-rendering path. Keep these local vendor assets available; use the project vendor lockfile if they need to be restored.

## 8. API route reference

The current route decorators in `app/web/main.py` define the canonical API. The finalizer emits a route inventory from that source into `reports/HADOTA_Closeout_Report.md`; consult that generated inventory if the table below and a future code change ever differ.

| Method | Route | Purpose |
|---|---|---|
| `GET` | `/api/health` | Web-process liveness; does not require the model to be available |
| `GET` | `/api/ready` | Checks local runtime availability and configured model readiness |
| `POST` | `/api/session` | Creates/returns an anonymous session and sets the cookie |
| `POST` | `/api/session/close` | Best-effort page-close signal; uses a grace period |
| `DELETE` | `/api/session` | Ends the caller's session and clears its cookie |
| `POST` | `/api/conversations` | Creates a new conversation in the caller's session |
| `GET` | `/api/conversations` | Lists conversations belonging to the caller's session |
| `GET` | `/api/conversations/{conversation_id}` | Retrieves a conversation only if it belongs to the current session |
| `DELETE` | `/api/conversations/{conversation_id}` | Deletes one owned conversation; a busy conversation can return `409` |
| `POST` | `/api/conversations/{conversation_id}/continue` | Continues an incomplete answer when continuation is available |
| `POST` | `/api/conversations/{conversation_id}/messages` | Sends a message and waits for the completed response (non-streaming web path) |

The exact schemas are defined in `app/web/schemas.py` and are enforced by FastAPI/Pydantic. Common response codes include `200`/`201` for successful operations, `401` when a required session is missing, `404` for a conversation that is absent or not owned by the caller, `409` for a busy conversation or a continuation state conflict, `413` for an oversized request body, `422` for invalid request data, `429` for generation capacity/rate limits, and `503` when runtime inference is unavailable or incomplete. The response bodies should be checked against the current schemas rather than inferred from generic examples.

### Health checks

```powershell
Invoke-RestMethod "http://127.0.0.1:8000/api/health"
Invoke-RestMethod "http://127.0.0.1:8000/api/ready"
```

`/api/health` is liveness; it is intended to remain responsive even if Ollama is down. `/api/ready` describes whether the configured runtime/model is available. Do not treat a successful health response as proof that generation can run.

## 9. Session, privacy and data lifecycle

- No login or registration is involved.
- A server-generated, opaque session cookie links the browser to its temporary session.
- Cookies are intended to be `HttpOnly` and `SameSite` restricted; public HTTPS mode requires the Secure flag.
- Each conversation belongs to a single session. Endpoints check ownership on the server.
- The default cap is 5 conversations per session and 25 active sessions in memory.
- Session idle expiry defaults to 15 minutes and absolute lifetime to 4 hours.
- The browser sends a best-effort close signal on page exit. Refresh/new activity can cancel the close grace period; the server TTL remains authoritative.
- Explicit End Session deletes the caller's session and clears the cookie.
- App process restart clears all memory-only sessions and conversations.
- Do not enter passwords, API keys, private credentials, or sensitive personal/financial information into a public demo.

## 10. Reliability issues identified and how they were addressed

The hardening work focused on correctness around concurrent access and resource use rather than replacing the architecture.

| Problem or risk | Implementation response | Evidence / remaining caveat |
|---|---|---|
| Conversation history could be read or changed concurrently | Added synchronization around message history snapshots/mutations | Regression suite; coverage does not prove all possible schedules |
| Failed/incomplete turns could leave confusing history | Added conditional rollback behavior in inspected normal, streaming-service and structured-output turns | Retry/conversation-service tests; keep browser streaming marked deferred |
| Two requests could mutate the same conversation | Per-conversation operation locks and non-blocking conflict handling | Busy-conversation tests; live concurrent-generation check recorded |
| Multiple visitors could all consume local inference simultaneously | Global active-generation semaphore set to one | A competing generation returned `429` in the live concurrency/retry check |
| Rate-limited or huge requests could consume unnecessary resources | Per-session and global generation rate windows, request-body limit and message limit | Test suite includes relevant controls; public exposure still requires broader adversarial verification |
| Chunked bodies could bypass a `Content-Length`-only check | Middleware accumulates and bounds received request chunks before forwarding | `tests/test_web_body_limit_chunks.py` was added and its tests collected; fresh finalizer results are in the closeout report |
| Session expiration/cleanup could race an active conversation | Deferred/ordered cleanup, conversation-operation locks, and a creation ownership recheck | Session cleanup/locking regression tests exist; final test output is authoritative |
| Refresh could delete a session immediately | Close signal has a short grace period; activity can preserve the session | Automated close-signal test exists; full real-browser lifecycle matrix remains limited |
| Health route depended on inference service | Separate liveness and readiness routes | API acceptance tests include health/readiness behavior |
| Internal exceptions/validation input could leak in responses | Generic validation errors, request IDs and basic security headers | Automated API and configuration tests; not a third-party penetration test |
| Continuation result could be attached to the wrong view after navigation | Reload active transcript when the original DOM node is detached | User manually verified continuation-after-navigation behavior |
| Retrying could duplicate the visible user message | Retry reuses the existing user message element | Live concurrency/retry acceptance check recorded one user turn and one assistant response |

## 13. Known limitations and explicitly deferred work

### Current limitations

- Browser chat uses non-streaming request/response; no browser SSE integration is claimed.
- Session and conversation state are memory-only and disappear on session expiry or FastAPI restart.
- The application depends on the local Windows PC, network, Ollama process and configured model.
- Only one model generation is allowed at a time by default. Additional attempts are intentionally rejected as busy/rate-limited.
- Dependency manifests use compatible ranges rather than an exact lock of every Python package.
- A 90% line-coverage number is evidence of executed lines, not a guarantee of correctness or security.
- There is no independent penetration test, production uptime guarantee, multi-process shared session store, or large-user performance benchmark.
- The current working copy was reported as not being a Git repository. Use explicit timestamped backups unless/until the project adopts version control deliberately.

### Deferred until infrastructure and resources are available

- Cloud/server hosting for FastAPI.
- Running Ollama and the Qwen 27B model on a suitable server/GPU, or using a separate hosted inference API.
- Public access through Tailscale Funnel.
- A separately hosted Vercel frontend.
- Browser streaming integration and a full streaming disconnect/error/terminal-event test matrix.
- Repeatable TTFT/completion-latency/throughput measurements.
- Broader real-device/mobile/accessibility/browser compatibility testing.
- Durable database-backed accounts/history, multi-instance scaling, observability, and formal production hardening.

These are future features, not incomplete claims about the currently delivered local design. The project remains usable as a local development/portfolio demonstration without online hosting.

## 14. Public-sharing safety note

**Do not turn on Tailscale Funnel or otherwise publish the app as part of this closeout.** Public sharing remains a separate future milestone.

A diagnostic run on 2026-10-24 showed Ollama listening on IPv6 unspecified address `::` at port `11434` and two enabled inbound Windows Firewall allow rules matching `ollama.exe`, scoped to the `Public` profile with broad port/address filters. The user chose not to change these during this closeout. This does not prove successful internet access to Ollama, but it is a known pre-publication risk that must be reviewed before exposing HADOTA to external users. The current local web server was observed on `127.0.0.1:8000`.

Before any future public deployment, revisit Ollama binding/firewall scope, verify that only the intended web endpoint is published, complete public-mode/origin/cookie/rate/TTL/lifecycle checks, test from a genuinely separate network, and prove the public endpoint can be disabled. Never expose Ollama port `11434` directly to the public internet.
